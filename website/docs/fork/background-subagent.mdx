# Background Subagent Mode

Run a subagent without blocking the LLM. The child `pi` process starts detached,
writes its result to disk, and the parent injects the result as a custom message
on the **next** turn. Useful for long-running work, fire-and-forget sweeps, and
parallel experiments where the parent should keep making progress.

## Quick start

Ask the LLM to delegate a task in the background:

```
Use the subagent tool with background: true, agent="scout", and
task="scan all files under packages/ for TODOs and report a count".
```

The tool call returns immediately with a task ID. The child runs detached. On
the parent's next turn, the result is injected as a custom message:

```
## [RUNTIME STATUS — subagent subprocesses | READ-ONLY]
…
| ID         | Type                 | Status     | Started | Elapsed | Last Output |
| ---------- | -------------------- | ---------- | ------- | ------- | ----------- |
| bg-3fa1b2c | pi-subprocess (scout) | **RUNNING** | 14:22 UTC | 1m     | 32 of 84 files scanned… |
```

The same status block is injected on every subsequent turn until the task
finishes. When it finishes, the final assistant message receives the child's
output as a custom message and the LLM can act on it.

## Parameters

The `subagent` tool gains two new parameters:

| Parameter     | Type    | Default | Description |
| ------------- | ------- | ------- | ----------- |
| `background`  | boolean | `false` | Fire-and-forget mode. The tool returns immediately with a task ID; the child runs in the background. Results are injected as a custom message on the next turn. |
| `script`      | string  | (none)  | Arbitrary shell script body to pass to the subagent as the task. The subagent LLM reads it and executes via its bash tool. Mutually exclusive with `task`; if both are provided, `script` wins. |

All other parameters (`agent`, `task`, `tasks`, `chain`, `agentScope`,
`confirmProjectAgents`, `cwd`) keep their existing semantics. `background: true`
works with single, parallel (`tasks`), and chain (`chain`) modes.

## Single mode (one task, one agent)

```js
subagent({
  background: true,
  agent: "scout",
  task: "Find every place we call the legacy Auth.verify() helper."
})
```

Returns immediately:

```
Background task bg-3fa1b2c started (scout, single). Use `/tasks` or `Ctrl+T`
to see live status; the result will be injected as a custom message on the next turn.
```

## Parallel mode (N tasks, N agents)

```js
subagent({
  background: true,
  tasks: [
    { agent: "scout",    task: "Map all HTTP routes in packages/server/src." },
    { agent: "scout",    task: "Map all DB queries in packages/server/src/db/." },
    { agent: "reviewer", task: "Audit the auth flow in packages/server/src/auth/." }
  ]
})
```

Returns:

```
Started 3 background tasks: bg-aaa, bg-bbb, bg-ccc. Use `/tasks` or `Ctrl+T`
to monitor. Results will be injected on the next turn.
```

Each task runs in its own `pi` subprocess. They run concurrently. The parent
does not block.

## Chain mode (sequential, with hand-off)

```js
subagent({
  background: true,
  chain: [
    { agent: "scout",    task: "Find the session store." },
    { agent: "planner",  task: "Design a Redis migration." },
    { agent: "worker",   task: "Implement the migration." }
  ]
})
```

The chain's first step starts immediately. Subsequent steps queue as
`pending` tasks. When step N finishes, step N+1 unblocks automatically and
runs as a fresh `pi` subprocess. The same task ID prefix is reused for each
step, suffixed with the step index (e.g. `bg-chain-0001`, `bg-chain-0002`,
`bg-chain-0003`).

## Runtime status block

The `before_agent_start` hook injects a read-only status block into every
parent turn. The block lists the currently active background tasks, with
their ID, type, status, start time, elapsed time, and last output preview.

When the registry is empty:

```
## [RUNTIME STATUS — subagent subprocesses | READ-ONLY]
No background subagent tasks are running.
Use `subagent({ background: true, ... })` to start a fire-and-forget task.
Use `/tasks` or `Ctrl+T` to view historical task logs.
Do not acknowledge this section unless you need to act on it.
```

When tasks are active, the block contains a markdown table plus an
"Available Actions" footer. The block is capped at 600 tokens
(~2,400 characters). If more than 10 tasks are active, the table shows
the first 10 and a "… N more running" hint directs you to `/tasks`.

The block is marked **READ-ONLY** explicitly. The LLM is instructed to
leave running processes untouched unless the user explicitly asks to
manage them. This prevents the model from "fixing" background tasks it
should not be touching.

## Dashboard (`/tasks` and `Ctrl+T`)

Open the live task dashboard in the TUI with either:

- the `/tasks` slash command, or
- the `Ctrl+T` keyboard shortcut

The dashboard renders a colour-coded list of every task in the registry
(running, completed, failed, cancelled, crashed), sorted newest-first. Each
row shows the task ID, the agent name, the elapsed time, and a 100-char
preview of the most recent output. The dashboard caps the visible list at
30 tasks; older tasks are summarised in a single footer line.

Press `Esc` to close the dashboard.

## On-disk state

Background tasks persist across process restarts. Two files live under
`~/.pi/agent/`:

```
~/.pi/agent/
├── subagent-registry.json          # task index (one JSON object)
└── subagent-logs/
    └── bg-<id>.log.jsonl           # per-task event log (one JSON per line)
```

The registry contains every task in any status. It is the single source of
truth for "what background tasks exist". The per-task log records every
event (spawn, model call, tool call, turn end, exit) as a JSONL stream.
Use it for archaeology when a task crashes or hangs.

The registry is pruned on `session_start`: any task that was `running`
when the previous session ended is marked `crashed` (see the next
section). After 24 hours, completed/failed/cancelled/crashed tasks are
removed from the registry on `session_start` (the per-task JSONL log
files are not pruned — they are kept for archaeology).

## Windows caveat

On Windows, child processes spawned by `Bun.spawn` (or
`node:child_process.spawn`) inherit the parent's Job Object and are
**terminated when the parent dies** — regardless of `detached: true` or
`unref()`. This is a Windows-specific kernel behaviour, not a bug in
the subagent code.

Practical consequences:

- **`pi -p "..."` foreground mode**: the parent exits as soon as the
  LLM's final response is delivered. Any background tasks spawned during
  that turn are killed at the same instant. The task record will show
  `crashed` (not `completed`) the next time `session_start` runs.
- **Interactive TUI (`pi` with no `-p`)**: the parent stays alive,
  so background tasks keep running normally. They are killed only when
  the TUI session itself ends (`session_shutdown` hook).
- **Recovery**: on `session_start`, every previously-`running` task is
  marked `crashed` with the message "Parent session ended (Windows
  terminates child processes with parent)". The on-disk log is preserved
  for post-mortem.

If you need long-running background work, use the interactive TUI, not
`pi -p`.

## Installation

The background-mode source lives in the fork-local extension
`packages/coding-agent/examples/extensions/subagent/`. The installed
location is `~/.pi/agent/extensions/subagent/`. The fork deploys the new
`background.ts` and `status-injector.ts` modules alongside the existing
`index.ts`, `agents.ts`, `ui.ts`, and the `agents/` + `prompts/`
directories.

After deploying, restart the `pi` TUI to pick up the new code. The
`/tasks` command and `Ctrl+T` shortcut are registered at extension
load time.

## Unit tests

The implementation ships with two unit test files:

- `background.test.ts` — 12 tests covering the registry, persistence,
  and crash-recovery behaviour
- `status-injector.test.ts` — 8 tests covering the status-block builder,
  the markdown escaping, and the token-budget cap

Run from the extension directory:

```bash
cd ~/.pi/agent/extensions/subagent
bun test
```
