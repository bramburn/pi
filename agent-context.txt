## Repository Overview

bramburn/pi is a fork of earendil-works/pi — a monorepo of TypeScript packages
that power an interactive coding-agent CLI / TUI. The relevant packages:

- `packages/ai` (`@earendil-works/pi-ai`) — provider-agnostic LLM abstraction;
  defines `Model<TApi>`, `Provider`, `MutableModels`, `createProvider`. Lazy

  host. Owns `AgentSession` and `ModelRuntime`.
- `packages/tui`, `packages/protocol`, `packages/client`, `packages/server` — UI
  / IPC layers (not touched by this goal).

Two remotes: `fork` (bramburn/pi, writable) and `origin` (earendil-works/pi,
read-only). Pushes go to `fork` only.

## Opinionated Architecture

- **Architecture pattern**: Layered monorepo. `ai` is the leaf, `coding-agent`
  is the application. Provider integration flows through `Models`/`MutableModels`.
- **Key layers**: `api/` (request shaping), `providers/` (catalogs), `Models`
  (registry + auth resolution), `ModelRuntime` (host-side wrapper that adds
  builtin providers + extension overrides), `AgentSession` (consumer).
- **State management**: `MutableModels` (in-memory `Map<string, Provider>` +
  optional `ModelsStore` for persistence). `ModelRuntime` layers a `builtins`
  map on top of extension-provided providers.
- **Dependency injection**: manual; constructor args + factory functions.
  `createProvider({ id, baseUrl, auth, models, api })` is the canonical pattern.
- **API / transport layer**: per-API `ProviderStreams` returned by lazy
  loaders (`openAICompletionsApi`, `anthropicMessagesApi`, …).
- **Data layer**: `ModelsStore` (default `InMemoryModelsStore`); persisted
  catalogs loaded via `loadProvidersFromModelsStore`.
